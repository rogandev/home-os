# Owner session gateway — draft, not ready for production

Browser requests use /api/data. A server-only bearer is forwarded to the fixed Railway API after an Auth0 owner session check. Explicit app route/method allowlists and same-origin checks restrict forwarding. This does not add upstream per-client scopes. FORM and connector credentials are unchanged.

## Required setup (separate approval)

Create an isolated Auth0 confidential Regular Web Application: authorization_code with PKCE S256, client_secret_basic, RS256, scope openid only. Verify the intended owner's immutable subject independently. No API audience, refresh token, offline_access or management grants. Configure Production-only server variables AUTH_ISSUER_URL, AUTH_CLIENT_ID, AUTH_CLIENT_SECRET, AUTH_SESSION_SECRET, AUTH_ALLOWED_SUBJECT, AUTH_BASE_URL, ROGAN_API_TOKEN. Never prefix secrets with VITE_. Client/session secrets must be unique per app; session secret must be cryptographically random (at least 32 random bytes encoded as base64url or hex).

The production origin is fixed in api/gateway.js. Auth0 allowed callback is that origin plus /api/auth/callback. Provider logout URLs, web origins and CORS origins need no entries for this server-side flow. App-local POST /api/auth/logout clears its own cookie and returns to /. Provider SSO remains active. Session cookies are Secure, HttpOnly, host-only, SameSite Lax with a one-hour rolling request-inactivity window and an eight-hour absolute maximum. Stateless cookies copied before logout remain valid until expiry; centralized revocation is not implemented. Preview deployments fail closed, including when production configuration is accidentally inherited.

## Verification and release gates

Run npm test, npm run test:auth and npm run build. Auth tests use a synthetic issuer and verify signature/claims, exact owner, cookies, expiry/logout, CSRF, route/method restrictions, no retry and browser bearer removal. Browser fixtures simulate sessions only in test code.

Before merging: verify actual Vercel function packaging/rewrites, sign-in with the intended owner and denial of another account, and all real consumer/payload constraints. Vercel Functions have a 4.5 MB request/response cap. Requests above 4,000,000 bytes are rejected locally before transmission. Large Trello migrations/exports and large unpaginated datasets require a separate compatible design or measured evidence; no truncation or blind splitting is acceptable. Real provider configuration and payload sizes have not been tested.

The review branch has git.deploymentEnabled:false only for codex/server-session-auth-review, preventing automatic preview deployment. Other branches retain their existing behavior. No live credentials/settings are configured by this change.

Coordinate shared API replacement only after every active consumer is accounted for. Keep Railway's staged replacement unapplied until then. Do not restore an exposed bearer or browser-token build as rollback. Keep a verified secure build with fresh credentials, or fail closed and repair forward. Reconcile uncertain writes before retrying. Existing persistent records, feature flags and connector scopes stay unchanged. Home OS must retain its public URL settings used for its prior IndexedDB journal namespace.

## Balanced sessions and memory-only draft recovery

Ordinary /api/auth/login permits provider SSO; /api/auth/switch alone forces prompt=login. Both request only openid, with no refresh token. The actual password/MFA interaction remains provider-dependent. Each authenticated request through SDK middleware can renew the one-hour idle window, including background requests; typing by itself cannot. There is no heartbeat or scheduled session-check polling. Session checks occur on initial load, explicit Check sign-in, or returning/completing sign-in while locked. An eight-hour original-login ceiling applies regardless of requests. Provider SSO may have separate plan/session limits.

On a 401/403 the transport blocks subsequent data requests and the gate locks/hides, but does not unmount, the app. Existing form state, selected import data and operation IDs therefore remain in the original tab. Sign-in deliberately opens another window and redirects that window through Auth0 to a fixed /api/auth/complete page. It never navigates the draft-bearing tab. The completion page communicates only a nonsecret wake-up signal; the original tab must independently verify its session and issuer/client/owner scope before restoring the editor. Wrong accounts remain locked, and a changed verified scope clears old memory before mounting fresh state. Native modal dialogs are closed during lock and restored only after verification.

Locked drafts are retained in memory for at most one hour, with expiry checked again on reentry (including after a suspended tab). They are not serialized to localStorage, sessionStorage, cookies, URLs or server storage. Reloading/closing the original tab loses unsaved drafts; the UI explains this and installs a before-unload warning. Explicit logout or account switching confirms discarding in-memory work. Existing durable recovery journals and saved user records are retained, not deleted. This intentionally uses a separate-window redirect rather than attempting to serialize every personal draft or a 19 MiB import. Browsers that block/open sign-in separately can use the link and Check sign-in; full live mobile/Safari validation remains required.

No operation is automatically replayed on unlock. Already forwarded operations may finish while the UI is locked; uncertain outcomes must be reconciled before the user explicitly retries the preserved intent. Copied stateless session cookies remain usable until idle/absolute expiry; a holder making requests can extend the idle window up to eight hours. Local logout does not revoke other copies or provider SSO. These are explicit limits of this design.
