# Combined Home OS device acceptance

This fixture renders the real combined `App.jsx` with copy, catalogs, supply and
delivery flags enabled. Every app request terminates in an in-memory model. No
credentials, production API, PostgreSQL executable or database are used. Reload
resets all sample changes. Fixture fidelity is for UI acceptance; API #86's actual
PostgreSQL CI remains the backend authority.

## Start when the device owner has UI focus

From the integration Home OS worktree, with the existing approved dependencies:

```sh
npm run dev:integration-fixture
```

Open `http://127.0.0.1:5196/fixtures/integration/index.html`. The server binds only
loopback, uses a strict port and does not replace another process. If the port is
occupied, coordinate with its owner; do not stop shared processes. Stop this server
with Ctrl-C after acceptance. No server is required to remain running for handoff.

The built fixture is generated by `npm run build:integration-fixture`. A physical
iPad/iPhone needs a separately approved route to this isolated fixture or an
authorized disposable test deployment. Do not expose the live inventory API for
this test and do not treat a production preview as a safe mutation target.

## Acceptance sequence

Record the frontend commit/tree and API86 CI head. Test phone 390×844 and iPad
820×1180 first, then the actual target device when an approved fixture route exists.

1. Confirm the disposable banner, both sample items, forecasts and an order due
   today. Check console errors and horizontal overflow, zoom, scrolling and touch
   targets. Capture inventory, an open editor, and the replacement confirmation.
2. Copy Face cream. Change only size; verify category, preferred room, description,
   policy and allocations remain editable/preserved. Cancel, Escape and backdrop
   dismissal must leave the item count and original stock unchanged.
3. Copy again and save. Confirm one independent item with preserved allocations,
   no copied incoming order, subscription, estimate or in-use history. Source item
   stock and its order remain unchanged. Rapid Save clicks create one copy.
4. Rename a category and room in Settings. Confirm stable-ID assignments and
   filters survive. Replacement deletion requires a chosen active destination;
   stock totals/container identities must not merge. Protected legacy rooms stay
   protected. The new copy must participate in the same catalog updates.
5. On Face cream, choose Opened a new one. No leaves the active unit and spares
   unchanged. Yes closes the existing usage and subtracts exactly one spare.
   Finished one closes usage without another subtraction. Reload to reset fixtures.
6. Edit an estimate, per-item warning and the global warning. Pause/resume/cancel
   subscription tracking; stock must remain unchanged. Check shortage and excess
   spare advisories. None may order, skip, or change a retailer automatically.
7. In Orders, change the expected delivery date, receive one unit into a selected
   container, then receive the remainder. Only confirmed receipts add stock. The
   partial order retains its remainder; completed linked delivery is not counted
   again as scheduled supply. Confirm the existing due-delivery actions remain usable.
8. Repeat with `VITE_HOME_CATALOG_MANAGEMENT=false` in a separate fixture config:
   canonical forms/filters remain, while Settings mutations disappear. Production
   default-off and this emergency build already have build coverage.

Lost-response copy recovery, stale edits, inactive-reference rejection and each
feature-off path have executable component/API coverage; fixture state is visible
at `window.__homeIntegrationFixture` for inspection. The fixture journal is memory
only; durable IndexedDB recovery has its separate catalog fixture and tests.

## Release and rollback handoff

Keep the parent hold: Flowboard restore gate, Dashboard, then Home OS. Review the
combined drafts as alternatives to the six earlier drafts; do not merge duplicates.
Check current main and rerun checks if it moves. Require a restorable snapshot,
backend migration/deployed-contract verification and device acceptance before
enabling flags. Production acceptance is read-only.

To withdraw copy/supply, disable their flags while retaining history. Once custom
catalog values exist, keep `VITE_HOME_CATALOGS=true` and the catalog-aware API;
disable only `VITE_HOME_CATALOG_MANAGEMENT`. Do not roll back to hard-coded pickers,
drop tables, restore consumed stock automatically, or repeat receipts.
